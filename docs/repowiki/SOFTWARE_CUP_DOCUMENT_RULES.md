# SOFTWARE CUP DOCUMENT RULES
# 软件杯文档规范约束层（Document Rules & Standards）

> 版本：v1.0 | 建立日期：2026-07-20  
> 来源：GB/T 8567-2006《软件工程 软件生存周期过程 文档化规范》+ 第十五届中国软件杯A3赛题要求  
> 用途：生成所有正式文档前必须参照本规则库，确保文档符合评审标准

## 一、核心约束原则（最高优先级）

### 原则一：工程真实性原则
- **所有内容必须来自项目代码、配置和数据**，不得虚构或推测
- 禁止写入未实现的功能，禁止夸大系统规模
- 正确示例：「后端基于 FastAPI 0.111.0，通过 sse-starlette 实现 SSE 流式推送」
- 错误示例：「系统采用微服务架构，支持千万级并发」（代码中无此架构）

### 原则二：评审友好性原则
- 文档面向**软件杯评审专家**，不是企业内部读者
- 重点体现：**创新价值 + 技术深度 + 工程完整度**
- 每份文档前 1 页必须让评审专家理解「这个系统的价值是什么」

### 原则三：AI 特色强化原则
- 本项目是 AI 教育系统，**必须专门描述 AI 相关设计**
- 普通软件工程文档结构 + AI 系统专有章节（Agent 设计、LLM 集成、RAG 架构）
- 切勿将 AI 特色淡化为普通功能描述

### 原则四：可追溯性原则
- 每个技术设计决策都必须对应到**具体代码文件或配置**
- 避免大篇幅空泛描述，每段后应有「实现位置：xxx.py」标注

## 二、GB/T 8567-2006 规范摘要（软件杯适用部分）

### 2.1 规范概述
GB/T 8567-2006 是中国软件工程文档化的国家标准，规定了软件生存周期过程中应产生的各类文档的格式和内容要求。软件杯明确要求「作品按照软件工程规范开发」，本规范为主要遵循依据。

### 2.2 文档体系结构

根据 GB/T 8567-2006，软件文档分为以下主要类型：

| 文档类型 | 标准代号 | 软件杯是否必须 |
|----------|----------|:------------:|
| 可行性分析报告（FAR） | FAR | 可选 |
| 软件开发计划（SDP） | SDP | 可选 |
| **软件需求规格说明书（SRS）** | SRS | **必须** |
| **软件概要设计说明书** | SDD | **必须** |
| **软件详细设计说明书** | DDD | **必须** |
| **数据库设计说明书（DBDD）** | DBDD | **必须** |
| **接口设计说明书（IDD）** | IDD | **必须** |
| 软件配置管理计划（SCMP） | SCMP | 可选 |
| **软件测试计划（STP）** | STP | **必须** |
| **软件测试说明** | STD | **必须** |
| **软件测试报告** | STR | **必须** |
| **软件安装部署说明** | SIS | **必须** |
| **用户操作手册（SUM）** | SUM | **必须** |
| 软件开发总结报告 | SDSR | 可选 |

### 2.3 各文档必含要素

#### SRS（软件需求规格说明书）必须包含：
1. **引言**：项目背景、建设目标、术语定义
2. **总体描述**：产品概述、用户特征、运行环境、假设与依赖
3. **功能需求**：各功能模块的详细输入/处理/输出描述
4. **非功能需求**：性能需求（响应时间、并发）、安全需求、可用性需求、可维护性需求
5. **接口需求**：用户界面接口、软件接口、硬件接口
6. **附录**：词汇表、需求跟踪矩阵

#### SDD（软件概要设计说明书）必须包含：
1. **系统总体架构**：部署架构、逻辑架构、数据流
2. **模块划分**：各模块职责、模块间接口
3. **数据架构**：数据库选型、主要实体关系
4. **接口设计**：外部接口（API）、内部接口
5. **安全设计**：认证鉴权、数据安全

#### DDD（软件详细设计说明书）必须包含：
1. **各模块详细设计**：类/函数设计、算法说明、数据结构
2. **接口详细规范**：请求/响应格式、错误码
3. **数据库详细设计**：表结构、索引设计、约束
4. **关键算法**：流程图或伪代码描述

#### 测试文档（STR）必须包含：
1. **测试环境**：软硬件配置、依赖版本
2. **测试用例**：输入、执行步骤、预期结果、实际结果
3. **测试结果统计**：通过/失败数量、覆盖率
4. **遗留问题**：未解决缺陷列表

#### 用户操作手册（SUM）必须包含：
1. **系统概述**：目的、范围、运行环境
2. **安装说明**：安装步骤、配置方法
3. **功能操作指南**：分角色（学生/助教/管理员）的操作流程
4. **故障排除**：常见问题与解决方案

## 三、软件杯 A3 赛题专项要求

### 3.1 评分权重（来自赛题规则）

| 评分维度 | 权重 |
|----------|:----:|
| 创新价值与实际意义 | 35% |
| 功能实现及技术要求 | 45% |
| 相关文档的丰富度 | 10% |
| 演示视频与 PPT 效果 | 10% |

### 3.2 功能要求与本项目对应关系

| 赛题要求功能 | 权重评估 | 本项目实现 | 文档重点 |
|------------|:--------:|------------|----------|
| ≥6维动态学生画像 | 高 | 8维 + mastery_map | SRS/SDD 专章描述 |
| 多智能体协同架构 | 高 | 8 Agent + Orchestrator | SDD Agent架构章节 |
| ≥5类个性化资源生成 | 高 | 6类（含信息图） | SDD/DDD 资源生成章节 |
| 个性化学习路径规划 | 高 | 知识图谱拓扑排序+DQN | DDD 算法章节 |
| 智能辅导答疑 | 中 | 流式对话+Challenger追问 | SRS/SDD 功能章节 |
| 学习效果评估 | 中 | 三层诊断引擎 | DDD 诊断引擎章节 |
| 视频脚本/多模态生成 | 中 | script/infographic类型 | SDD 资源生成章节 |
| 可信机制（防幻觉） | 中 | 越界拦截+引用溯源 | DDD 信任机制章节 |

### 3.3 文档提交要求

根据赛题规则，参赛队伍提交的文档应：
1. **参照 GB/T 8567-2006**（即本规范所依据的标准）
2. 包含：系统说明书、设计说明书等（含系统实现、用户界面等细节说明）
3. 突出说明：**前沿 AI 技术在系统中的融合思路、实现方案**
4. 同时指出：系统存在的**待改进之处**（真实性原则）
5. 推荐通过：图表、架构图、流程图、可视化增强文档可读性
6. 文档格式统一，逻辑清晰，具有参赛价值和商业支撑

### 3.4 AI 特色文档特别要求

由于 A3 赛题的核心是 AI 系统，以下章节在所有文档中均须**强化描述**：

#### AI 系统专项描述要求
- 所有功能文档必须说明：**哪些功能由 AI 完成，AI 如何做到**
- 技术文档必须包含：**Prompt 工程设计思路**（不展示具体 Prompt 内容，只描述设计原则）
- 架构文档必须包含：**LLM 调用流程 + 降级容错机制**
- 测试文档必须包含：**AI 诊断准确率测试**（不只是功能测试）

#### 禁止项
- 不得将 LLM 使用描述为「调用 AI API」一笔带过
- 不得省略 RAG 架构描述（这是技术亮点，必须详述）
- 不得忽略多 Agent 协同机制（这是赛题核心要求）

## 四、文档格式规范

### 4.1 文档头部统一格式

每份正式文档开头必须包含：

```markdown
# [文档名称]

| 项目 | 内容 |
|------|------|
| 项目名称 | Socrates-Cube 多智能体自适应学习系统 |
| 文档版本 | v1.0 |
| 编制日期 | YYYY-MM-DD |
| 适用阶段 | 软件杯 A3 赛题参赛版本 |
| 参考规范 | GB/T 8567-2006 |
```

### 4.2 章节编号规范
- 一级章节：`## 一、标题`（中文数字）
- 二级章节：`### 1.1 标题`（阿拉伯数字）
- 三级章节：`#### 1.1.1 标题`
- 表格、图片均须有编号和标题（如「表 3.1 数据表清单」）

### 4.3 图表要求
- 架构图必须包含（优先级排序）：
  1. 系统总体架构图（含前后端、数据库、LLM）
  2. 多 Agent 协同流程图
  3. 三层诊断流程图
  4. 数据流图（用户请求 → SSE 响应）
- 数据库设计必须包含 ER 图（可用 Mermaid 描述关系）

### 4.4 代码与接口描述规范
- API 接口描述格式：
  ```
  接口名称：[名称]
  请求方法：GET/POST
  路径：/api/v1/xxx
  请求参数：[字段名] [类型] [必填] [说明]
  响应格式：[JSON结构]
  说明：[功能描述]
  ```
- 不直接在文档中展示完整代码，只展示关键接口签名和数据结构

## 五、各文档专项写作规则

### 5.1 SRS（软件需求规格说明书）写作规则

**必须包含的内容**（对应本项目）：
- [ ] 项目背景：高校计算机网络课程学习痛点 + A3 赛题解题思路
- [ ] 9 个功能需求（F01-F09）的完整描述，包含验收标准
- [ ] 非功能需求：响应时间（SSE <500ms 开始输出）、并发（支持多用户同时对话）
- [ ] 用户角色描述（学生/助教/教师）

**禁止包含的内容**：
- 不得描述未实现功能（SeeDance 视频生成已确认不接入）
- 不得夸大性能指标（只写实际测试验证的数字）

**写作提示**：
- 重点突出三层诊断的需求来源（传统问答系统的局限性）
- 量化验收标准（如「course_docs ≥ 30 块，诊断响应 <3s」）

### 5.2 SDD（软件概要设计说明书）写作规则

**必须包含的内容**：
- [ ] C4 架构设计（Context → Container → Component 三层）
- [ ] 8 Agent 架构设计与协同机制
- [ ] SSE 事件流设计
- [ ] RAG 知识库架构
- [ ] 技术选型理由（为什么选 FastAPI、为什么选 ChromaDB）

**AI 特色章节（必须单独成章）**：
- 多 Agent 协同架构设计（Orchestrator 模式说明）
- Prompt 工程设计思路（不展示具体内容，描述设计原则）
- LLM 容错降级机制（Mock 模式、兜底内容）

### 5.3 DDD（软件详细设计说明书）写作规则

**必须包含的内容**：
- [ ] 三层认知诊断算法详细说明（伪代码 + 错误类型枚举）
- [ ] 知识图谱拓扑排序算法（Kahn 算法流程图）
- [ ] 资源生成认知风格适配逻辑（STYLE_PRIORITY 映射表）
- [ ] 画像更新混合策略（确定性增量 + LLM 全量校准）
- [ ] TTL 缓存设计（5 分钟 + 200 条上限）

**注意**：不要将算法描述成「使用 AI 生成」，要具体到函数名、参数、返回值

### 5.4 数据库设计说明书写作规则

**必须包含的内容**：
- [ ] 11 张表的完整字段说明（包含数据类型、约束、索引）
- [ ] 核心实体关系（User → Profile，Session → AgentLog，Path → PathNode）
- [ ] 知识图谱 JSON 结构说明（非关系型存储）
- [ ] 向量数据库集合设计（4 个集合 + 降级方案）

**禁止内容**：
- 不要描述未实现的 Redis 缓存、Elasticsearch 等

### 5.5 测试文档写作规则

**必须包含的内容**：
- [ ] 测试环境：Python 3.10，pytest 8.2，59 条测试用例全通过
- [ ] AI 功能测试用例（三层诊断准确率测试）
- [ ] 接口测试用例（核心 API 的正常/异常路径）
- [ ] 前端构建测试（vue-tsc 0 errors，vite build 成功）
- [ ] Mock 模式离线功能验证

**特殊要求**：
- 测试报告必须包含「AI 诊断准确率」测试（可引用 `docs/results/diagnosis_accuracy_phase4.md`）
- 必须说明降级容错测试（LLM 不可用时的 Mock 模式验证）

### 5.6 用户手册写作规则

**必须包含的内容**：
- [ ] 三种启动方式（一键启动/手动启动/Docker）
- [ ] 学生角色操作流程（登录→新手引导→对话→查看诊断→获取路径→资源学习）
- [ ] 协议仿真使用说明（7 个场景的操作步骤）
- [ ] 常见问题（ChromaDB 不可用/LLM API 未配置/端口冲突）
- [ ] 演示账号说明（3 个预置账号）

## 七、写作禁忌清单（评审扣分项）

### 7.1 内容真实性问题
- ❌ 描述未实现的功能（如「支持视频生成」但代码中 SeeDance 未接入）
- ❌ 夸大系统容量（如「支持万级用户并发」但实际是单机 SQLite）
- ❌ 虚构测试数据（如「诊断准确率 95%」但未实际测试）
- ❌ 描述概念性架构而非实际架构（如写了微服务但代码是单体）

### 7.2 软件工程规范问题
- ❌ 缺少验收标准的功能需求描述
- ❌ 数据库设计没有字段类型和约束说明
- ❌ 接口文档没有请求/响应格式示例
- ❌ 测试文档只有通过/失败，没有测试用例描述

### 7.3 AI 特色缺失问题
- ❌ 只说「系统使用了大语言模型」不说怎么用
- ❌ 不描述 RAG 架构（仅说「知识库支持问答」）
- ❌ 不说明多 Agent 协同机制（只说「系统有多个模块」）
- ❌ 不描述 Prompt 工程设计思路

### 7.4 格式规范问题
- ❌ 没有统一的文档头部信息
- ❌ 图表没有编号和标题
- ❌ 章节结构混乱，不符合 GB/T 8567-2006 章节要求
- ❌ 中英文混排不统一（专业术语可保留英文，但说明文字应为中文）
