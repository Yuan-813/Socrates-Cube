# Socrates-Cube 答辩问答准备

> 预判 20 个常见问题及标准答案，覆盖创新性、技术方案、实现细节、应用价值

---

## 一、创新性相关（5 题）

### Q1：你们的三层诊断和传统 LLM 直接问诊有什么区别？

**答**：传统 LLM 问诊是一次性调用，输出非结构化文本，无法保证诊断深度和一致性。我们的三层诊断是结构化流水线：

1. **第一层（表层错误识别）**：先判断对错，再归类到 7 种错误类型之一（流程遗漏、层级错位、概念混淆等），而不是笼统地说"你说错了"。
2. **第二层（根因溯源）**：结合知识图谱上下文，分析错误的深层原因和缺失的前置知识。比如学生说"TCP 两次握手就够"，我们不只说"不对"，而是定位根因——未理解第三次 ACK 防止历史失效连接的作用。
3. **第三层（模式匹配）**：将错误映射到 7 种已知误区模式，生成针对性的干预建议。这使得系统能从"纠错"升级为"纠偏"。

每层都有独立的 prompt 和结构化 JSON 输出，且有类型兜底保证一致性。

---

### Q2：多智能体架构相比单 Agent 有什么优势？为什么不直接用一个 LLM 做所有事？

**答**：单 Agent 架构存在三个问题：

1. **Prompt 膨胀**：把检索、诊断、画像、资源生成全塞进一个 prompt，导致 token 数爆炸、LLM 输出质量下降。
2. **不可调试**：出问题时无法定位是哪个环节出错。
3. **不可扩展**：新增功能需要改整个 prompt。

我们的 8 Agent 架构将职责拆分：每个 Agent 有独立 prompt、独立输入输出、独立日志，支持单元测试。Orchestrator 做状态机调度，Agent 之间通过结构化数据传递，而非自然语言。这样既提升了输出质量，也使全链路可追溯、可调试。

---

### Q3：知识图谱驱动的路径规划和普通推荐算法有什么不同？

**答**：普通推荐算法基于协同过滤或内容相似度，输出的是"推荐什么"，但不解释"为什么推荐"。我们的路径规划有三个本质区别：

1. **拓扑排序保证顺序合理性**：基于知识图谱的 21 条前置依赖边，确保学生先学前置知识。
2. **三维推荐理由可解释**：每个节点附带 graph_dependency（图谱依赖链）、diagnosis_result（诊断关联）、cognitive_style（风格匹配），推荐理由可追溯。
3. **画像驱动动态调整**：路径不是静态的，每轮对话后画像更新，路径中的节点状态（completed/in_progress/pending/locked）也会动态变化。

---

### Q4：你们的认知画像和已有学习分析系统有什么区别？

**答**：传统学习分析系统主要基于答题正确率，维度单一。我们的画像有三大区别：

1. **8 维认知能力**：不只看"对不对"，还评估概念理解、协议分析、计算能力、错误诊断、系统设计、知识关联、表达清晰、自我修正 8 个维度。
2. **混合更新策略**：每轮对话做确定性增量更新（无需 LLM，延迟 <50ms），每 5 轮做 LLM 全量校准（去抖 10s），兼顾实时性和准确性。
3. **认知风格识别**：区分 visual / practical / textual 三种风格，驱动资源生成优先级——视觉型优先思维导图，实践型优先代码练习。

---

### Q5：苏格拉底式追问是怎么实现的？和直接给答案有什么区别？

**答**：苏格拉底式追问是系统回复的核心风格。当学生提问时，系统不直接给出标准答案，而是：

1. 先通过诊断引擎分析学生的误区
2. 基于误区设计反例或追问场景（如"如果只有两次握手，服务端如何确认客户端收到了 SYN+ACK？"）
3. 引导学生自己推理出正确答案

实现上是在 Orchestrator 的流式回复 prompt 中注入诊断结果和追问策略模板，让 LLM 以苏格拉底风格生成回复。这样不仅纠正错误，还培养学生的推理能力。

## 二、技术方案相关（7 题）

### Q6：你们用的什么 LLM？为什么选这个？

**答**：我们使用讯飞星火大模型（Spark AI），通过 `spark-ai-python` SDK 调用。选择原因：

1. **中文能力强**：计算机网络课程涉及大量中文术语，星火在中文理解上优于部分海外模型。
2. **API 稳定**：提供免费配额，适合竞赛和教学场景。
3. **支持流式输出**：SDK 支持 SSE 流式响应，适配我们的实时推送需求。

同时我们做了 LLM 无关化设计——通过 `llm_client` 抽象层封装，可快速切换到其他 LLM（如 GPT、文心一言），只需修改一个文件。

---

### Q7：向量数据库用的什么？为什么不用 ChromaDB？

**答**：我们支持两种方案：

1. **ChromaDB（可选）**：安装 `requirements-vector.txt` 后可用，提供完整向量检索能力。
2. **本地 JSON 索引（默认）**：不依赖 ChromaDB，使用 `data/vector_db/local_index.json` 做 TF-IDF + 关键词匹配的轻量检索。

默认使用本地索引的原因：竞赛演示环境通常无法安装 ChromaDB 的依赖（需要 C++ 编译器），本地索引保证了"开箱即用"。同时 Retriever 有兜底数据，即使检索完全失败也能返回预设常用知识点。

---

### Q8：知识图谱是怎么构建的？有多少节点？

**答**：知识图谱包含 **20 个知识点节点**和 **21 条前置依赖边**，覆盖《计算机网络》课程的 5 个章节：

- 第1章 概述：网络分层、协议体系等
- 第3章 传输层：TCP/UDP、握手挥手、滑动窗口
- 第4章 网络层：IP、ICMP、路由
- 第5章 数据链路层：MAC、ARP
- 第6章 应用层：HTTP、DNS

图谱数据存储在 `data/knowledge_graph.json`，支持前置依赖查询、拓扑排序、关键词检索、掌握度估算。构建方式是人工编辑 + 课程大纲对齐，确保依赖关系的正确性。

---

### Q9：SSE 流式推送是怎么实现的？有哪些事件类型？

**答**：使用 `sse-starlette` 库实现 Server-Sent Events，共 10 种事件类型：

| 事件类型 | 说明 |
|---------|------|
| `agent_start` | Agent 开始执行 |
| `agent_end` | Agent 执行完成 |
| `tool_call` | Agent 调用工具（如知识图谱查询） |
| `token` | 流式回复文本片段 |
| `diagnosis` | 三层诊断结果 |
| `resource` | 资源生成结果 |
| `path_update` | 学习路径更新 |
| `state_change` | 对话状态机变化 |
| `done` | 本轮对话完成 |
| `error` | 错误通知 |

前端通过 EventSource 监听这些事件，实时渲染 Agent 状态栏、诊断面板、资源卡片等组件。

---

### Q10：Mock 模式是怎么实现的？能完全离线运行吗？

**答**：Mock 模式通过 `MOCK_MODE=true` 环境变量或 `--mock-mode` 命令行参数启动：

1. **后端**：`mock_provider.py` 实现了 LLM 接口的 Mock，返回预置的结构化响应（诊断结果、资源内容等），无需 API Key。
2. **前端**：`mockInterceptor.ts` 拦截所有 API 请求，返回 `public/mock/` 目录下的 JSON 文件，模拟完整的 SSE 事件流。
3. **数据库**：使用 SQLite 本地文件，无需额外数据库服务。

两种 Mock 可以独立或组合使用。完全 Mock 模式下，系统可以离线运行全链路演示：对话→诊断→资源→路径→画像→仿真。

---

### Q11：前端技术栈为什么选 Vue 3 + Tailwind + Element Plus？

**答**：

1. **Vue 3**：Composition API + `<script setup>` 语法，开发效率高；Pinia 状态管理轻量直观。
2. **Tailwind CSS**：原子化 CSS，快速实现响应式布局和自定义视觉风格，无需维护大量 CSS 文件。
3. **Element Plus**：提供成熟的数据表格、对话框、表单等组件，减少 UI 造轮子。
4. **ECharts**：雷达图、热力图等可视化效果好。
5. **Vite**：开发热更新快，构建性能好。

整体技术栈偏轻量，适合竞赛项目快速迭代。

### Q12：数据库设计是什么样的？

**答**：使用 SQLite + SQLAlchemy ORM，共 5 张表：

| 表名 | 说明 |
|------|------|
| `sessions` | 对话会话 |
| `messages` | 对话消息 |
| `student_profiles` | 学生画像 |
| `learning_paths` | 学习路径 |
| `agent_logs` | Agent 运行日志 |

设计原则：读写分离优化（画像更新用异步写入），agent_logs 表记录每个 Agent 的入参、出参、耗时，支持全链路追溯。数据库文件 `edu_agent.db` 随项目提交，预置了 3 个演示账号。

## 三、实现细节相关（5 题）

### Q13：三层诊断的每层 LLM 调用是怎么保证 JSON 输出一致性的？

**答**：三层保障：

1. **Prompt 约束**：每层 prompt 明确要求输出 JSON 格式，并给出字段说明和示例。
2. **JSON 解析容错**：使用 `json.loads` + try/except，解析失败时尝试提取 `{...}` 片段再解析。
3. **类型兜底**：解析成功后做类型检查——`pattern` 如果是 str 则包装为 dict，`root_causes` 如果不是 list 则转换为 list，`missing_prerequisites` 同理。确保下游消费者拿到的始终是正确类型。

```python
if isinstance(pattern, str):
    pattern = {"pattern": pattern, "intervention_suggestion": "建议先用对比题澄清概念边界。"}
if not isinstance(pattern, dict):
    pattern = {}
```

### Q14：画像更新的去抖机制是怎么实现的？

**答**：去抖窗口 10 秒，实现逻辑：

1. 每轮对话后调用 `profiler.update()`，先做确定性增量更新（调整 mastery_map、维度分数），这一步不需要 LLM，延迟极低。
2. 记录更新时间戳，如果距离上次 LLM 全量校准不足 10 秒，跳过 LLM 调用。
3. 超过 10 秒且对话轮次达到 5 的倍数时，触发 LLM 全量校准——将最近 5 轮对话和当前画像传入 LLM，生成校准后的画像。

这样可以避免学生在短时间内连续提问导致频繁 LLM 调用，同时保证画像的时效性。

---

### Q15：可信溯源机制是怎么实现的？

**答**：三层可信机制：

1. **范围校验**：`trust_mechanism.py` 实现双层判断——先做关键词匹配（如"数学题"、"物理公式"直接拒答），再由 LLM 判断是否超出计算机网络课程范围。越界时返回友好提示，不调用下游 Agent。
2. **来源溯源**：Retriever 返回的每条文档都带有 source 字段，Orchestrator 在回复末尾拼接参考来源列表（如"参考来源：[1] 谢希仁《计算机网络》第8版 第5章"）。
3. **不确定性声明**：诊断置信度低于 0.6 时，自动在回复中追加"以上分析仅供参考，建议结合教材确认"的声明。

---

### Q16：资源生成如何根据认知风格调整？

**答**：ResourceGenerator 的 `generate_all()` 方法接收 cognitive_style 参数：

| 认知风格 | 优先资源类型 | 生成策略 |
|---------|------------|---------|
| visual（视觉型） | 思维导图 > 视频脚本 > 文档 | Mermaid 图 + 结构化视频脚本 |
| practical（实践型） | 代码示例 > 练习题 > 文档 | Python 可运行代码 + 选择题 |
| textual（文本型） | 知识文档 > 练习题 > 代码 | Markdown 长文档 + 简答题 |

同时，诊断结果会强制追加针对性资源——如流程遗漏型错误自动追加仿真推荐资源，概念混淆型自动追加对比题资源。

---

### Q17：演示环境如果 LLM 超时了怎么办？

**答**：三级降级策略：

1. **LLM 超时降级**：Orchestrator 的 LLM 调用设置 30 秒超时，超时后返回友好提示"回答生成超时，正在使用缓存回复"，并尝试使用 Mock 响应兜底。
2. **Agent 异常降级**：每个 Agent 的调用都有 try/except，失败后返回默认结构化数据，不影响其他 Agent 执行。如 ResourceGenerator 失败时调用 `_fallback_content()` 返回预设资源。
3. **完全 Mock 模式**：如果后端完全不可用，前端 mockInterceptor 自动接管，模拟完整 SSE 事件流。Ctrl+Shift+D 可快速切换演示模式。

演示脚本中预置了应急预案，确保 7 分钟演示不中断。

## 四、应用价值与展望（3 题）

### Q18：这个系统能用于实际教学吗？

**答**：可以。当前版本已经覆盖了计算机网络课程的核心知识点（TCP/IP、HTTP、DNS 等），支持：

1. **课堂辅助**：教师可使用系统的诊断面板了解全班常见误区，针对性调整教学。
2. **课后自学**：学生可通过智能对话获得个性化辅导，不受时间和地点限制。
3. **学习路径推荐**：系统自动生成学习路径，帮助学生查漏补缺。

需要改进的方面：扩展到更多课程科目、对接教务系统实现真实成绩数据集成、增加教师管理后台。

---

### Q19：系统的主要瓶颈在哪里？如何优化？

**答**：当前主要瓶颈：

1. **LLM 调用延迟**：三层诊断需要 3 次 LLM 调用，加上回复生成共 4 次。优化方向：合并第一层和第二层的 prompt，减少到 2 次调用；使用更快的 LLM API。
2. **向量检索精度**：本地 JSON 索引使用 TF-IDF，精度不如 Embedding。优化方向：部署 ChromaDB + 预计算 Embedding。
3. **画像更新频率**：去抖窗口 10 秒在高频对话时可能不够灵敏。优化方向：根据对话密度动态调整去抖窗口。
